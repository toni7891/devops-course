# Release Engineering Lab — `company-api`

## Scenario

The backend team has handed you a working NestJS service called `company-api`. It compiles, the tests pass, it exposes three endpoints:

- `GET /health` — liveness probe
- `GET /version` — reads `APP_VERSION`, `COMMIT_SHA`, `BUILD_DATE` from the environment and returns them as JSON
- `GET /users` — CRUD scaffold

**You are the DevOps engineer.** Your job is not to write the application. Your job is to **take this existing system and put it into a real release process** — the same process that exists at every company that ships software in containers.

You will build:

1. A multi-stage **Dockerfile** that produces a small, secure, traceable image.
2. A multi-job **GitHub Actions workflow** that tests, builds, publishes the image to a container registry, and uploads a release manifest as an artifact.

Expected time: **6–10 hours**.

## Prerequisites

Before you start, confirm you have these installed and configured:

- **Docker** (`docker --version`) — for building and testing the image locally. Docker Desktop on Windows/macOS, or the engine on Linux.
- **Node.js 20** (`node --version`) — for running `npm test` and `npm run build` locally.
- **Git** (`git --version`).
- **GitHub account** with permission to create a repo.
- **GitHub CLI** (`gh --version`) is highly recommended — the lab uses it for repo creation, scope grants, and watching workflow runs.

### One non-obvious gh-CLI prerequisite

If you use `gh` to push, your token must have the `workflow` scope — otherwise GitHub will reject any push that adds or modifies files under `.github/workflows/` with the error *"refusing to allow an OAuth App to create or update workflow ... without `workflow` scope."*

Grant the extra scopes once, up front:

```bash
gh auth refresh -s workflow,write:packages
```

The `write:packages` scope is needed if you later want to push to GHCR from your local machine (the in-CI push uses `GITHUB_TOKEN` and doesn't need this). Granting both now avoids a second round-trip.

## Part 1 — Versioning

There is **no automatic versioning** in this lab. No SemVer bots, no conventional-commits parsing, no changelog generation.

The version is whatever is written in [package.json](package.json):

```json
{ "name": "company-api", "version": "1.0.0" }
```

If you want to release `1.1.0`, you edit `package.json`, commit it, push it. That commit's version is `1.1.0`. This is on purpose — you are learning **release control**, not release automation. Release automation is a layer on top of what you build here.

Your pipeline extracts the version from `package.json`. Hint:

```bash
node -p "require('./package.json').version"
```

## Part 2 — Dockerfile recipe

You will build a **three-stage** Dockerfile. Each stage has a goal, a list of required behaviors, and the *why* behind each requirement. **Do not skip the why** — every line you write should be defensible if asked "why is this here?"

### Stage 1: `deps` — install dependencies

**Goal:** a cached layer containing `node_modules` derived from `package.json` + `package-lock.json` only.

**Required:**
- Base image: `node:20-alpine`.
- Working directory: `/app`.
- Copy **only** `package.json` and `package-lock.json` (use a glob; do not copy source code yet).
- Install with the strictly-reproducible install command — the one that requires `package-lock.json`, never mutates it, and is faster than `npm install`.

**Why:** Splitting "install deps" from "copy source code" is what makes the Docker layer cache effective. Source changes on every commit; dependencies rarely do. Copying manifests first means the slow install step is only re-run when dependencies actually change.

### Stage 2: `builder` — compile and prune

**Goal:** a stage that has produced `dist/` and contains a `node_modules` with **only runtime dependencies** (no devDeps).

**Required:**
- Base image: `node:20-alpine` (same as `deps`).
- Reuse `node_modules` from the `deps` stage — copy it with `COPY --from=deps`, do **not** reinstall.
- Copy `tsconfig.json`, `tsconfig.build.json`, `nest-cli.json`, and the `src/` directory.
- Run the `build` script from `package.json`.
- **After** the build, prune dev dependencies so the surviving `node_modules` is runtime-only.

**Why pruning matters:** The runtime image (next stage) is **distroless** — it has no shell, no `apt`, and crucially **no `npm`**. You cannot reinstall packages in the runner. The pruned `node_modules` from this stage is what the runner inherits.

### Stage 3: `runner` — distroless production image

**Required base image — non-negotiable:**

```
gcr.io/distroless/nodejs20-debian12:nonroot
```

**Why this exact image:**
- **distroless** — no shell, no package manager, no busybox. Attack surface is approximately "Node.js + your app." Standard for production Node containers.
- **`nodejs20`** — must match the Node major used to compile your code. A mismatch (compile on 20, run on 18) causes runtime errors.
- **`:nonroot`** — pre-creates a non-root user (UID 65532). Running containers as root is the most common containerization mistake; this tag eliminates it with zero work.

**Required behaviors:**

1. Set the working directory to `/app`.
2. Set `ENV NODE_ENV=production` (many libraries take faster code paths under this flag).
3. Copy three things from `builder`:
   - `node_modules` (the pruned tree)
   - `dist/` (the compiled app)
   - `package.json` (Node uses it for runtime resolution: `"main"`, `"type"`, etc.)
4. Declare three build args:

   ```
   ARG VERSION=dev
   ARG COMMIT_SHA=unknown
   ARG BUILD_DATE=unknown
   ```

   Each must have a default so the file builds without `--build-arg`. **The defaults must be visibly wrong** (`dev`, `unknown`) — if you forget to pass build args in CI, `/version` will return `"dev"` and you'll catch it immediately.

5. Convert each `ARG` to a runtime `ENV`. **The env var the app reads is `APP_VERSION` — not `VERSION`.** `COMMIT_SHA` and `BUILD_DATE` keep their names.

   ```dockerfile
   ENV APP_VERSION=$VERSION
   ENV COMMIT_SHA=$COMMIT_SHA
   ENV BUILD_DATE=$BUILD_DATE
   ```

   **Why this two-step:** `ARG` is build-time only — it disappears at runtime. The app reads `process.env.APP_VERSION` at runtime, so the build arg must be promoted into an env var. This is the canonical pattern for baking build metadata into a running image.

   **Why `APP_VERSION` and not `VERSION`:** `VERSION` is a common name that some base images set themselves (e.g., distro version). Renaming to `APP_VERSION` avoids the collision. Look at [src/version/version.controller.ts](src/version/version.controller.ts) — that's what the app reads.

6. Add three OCI standard labels, populated from the build args:

   - `org.opencontainers.image.version`
   - `org.opencontainers.image.revision`
   - `org.opencontainers.image.created`

   **Why OCI labels in addition to ENV:** ENV is for the running app to read. Labels are for **registry tooling** to read — `docker inspect`, the Docker Hub / GHCR web UI, vulnerability scanners, SBOM generators. Labels make the metadata discoverable without running the container.

7. Set `USER nonroot` explicitly. (The `:nonroot` tag already does this; setting it again is belt-and-braces.)
8. `EXPOSE 3000`.
9. **`CMD ["dist/main.js"]` — NOT `["node", "dist/main.js"]`.**

   This is the single sharpest edge in the file. Distroless Node images set `node` as the **entrypoint**. Anything in `CMD` is passed as arguments to `node`. So `CMD ["node", "dist/main.js"]` would execute `node node dist/main.js` and fail with "Cannot find module 'node'".

### `.dockerignore`

You must also create a `.dockerignore` at the repo root.

**Why:** Without one, Docker sends your entire repo as the "build context" — including `node_modules` (huge), `.git/` (huge), `.env` files (sensitive), `dist/` (stale). This bloats builds and risks leaking secrets into image layers.

**Minimum entries:** `node_modules`, `dist`, `.git`, `.github`, `coverage`, `*.log`, `.env*`.

### Local acceptance tests — run all six before pushing

```bash
# 1. Build succeeds with all three build args
docker build \
  --build-arg VERSION=1.0.0 \
  --build-arg COMMIT_SHA=abc1234 \
  --build-arg BUILD_DATE=$(date -u +%Y-%m-%dT%H:%M:%SZ) \
  -t company-api:test .

# 2. /version returns injected values (NOT "dev" or "unknown")
docker run -d --rm --name capi -p 3001:3000 company-api:test
sleep 2
curl -s localhost:3001/version
# Expected: {"version":"1.0.0","commit":"abc1234","buildDate":"..."}

# 3. OCI labels populated
docker inspect company-api:test --format '{{json .Config.Labels}}'

# 4. Runs as non-root
docker inspect company-api:test --format '{{.Config.User}}'
# Expected: nonroot

# 5. Image size under 250 MB
docker images company-api:test --format '{{.Size}}'

# 6. No shell exists (proves distroless)
docker run --rm --entrypoint="" company-api:test sh
# Expected: error — "exec: \"sh\": executable file not found in $PATH"
#
# NOTE: --entrypoint="" is required because distroless Node images set
# `node` as the entrypoint. Without overriding it, the container would
# instead try to run `node sh`, which fails with the misleading error
# "Cannot find module '/app/sh'" — same conclusion (no shell exists),
# but the error message obscures what's actually being tested.

docker stop capi
```

If all six pass, your Dockerfile is done. Move on to the workflow.

## Part 3 — Workflow recipe

You will build one workflow file: `.github/workflows/release.yml`. It runs on `push` to `main` and has **four jobs** chained in strict order:

```
test  →  build  →  docker-release  →  release-artifact
```

Each job's `needs:` must reference the previous one. If a job fails, downstream jobs do not run. This is not decoration — it is the lab's CI/CD orchestration lesson.

### Job 1: `test`

**Goal:** Prove the code compiles and tests pass before anything else runs.

**Required steps:**
- `actions/checkout@v4`
- `actions/setup-node@v4` with `node-version: 20` and **`cache: 'npm'`** (this is one of two required cache layers).
- `npm ci`
- `npm test`

**Why the npm cache:** Faster installs across workflow runs. Reinforces the same "dependency-layer awareness" you applied in the Dockerfile's `deps` stage — applied here at the CI level.

### Job 2: `build`

**Depends on:** `test`.

**Goal:** Prove `npm run build` succeeds. This job exists to fail fast on TypeScript errors **before** you pay for a Docker build (which is much slower). No artifact upload here — the Docker job rebuilds from source.

**Required steps:** Same checkout + setup-node + npm cache, then `npm ci` and `npm run build`.

### Job 3: `docker-release`

**Depends on:** `build`.

**Goal:** Build the image with metadata baked in, push it to your registry under both required tags, capture the registry digest for the next job.

**Required steps (in order):**

1. `actions/checkout@v4` with `fetch-depth: 0` (needed so `git rev-parse` sees real history, not just the latest commit).
2. **Extract the version** from `package.json` into a step output:
   ```bash
   echo "version=$(node -p "require('./package.json').version")" >> "$GITHUB_OUTPUT"
   ```
3. **Extract the short commit SHA** into a step output:
   ```bash
   echo "sha=$(git rev-parse --short HEAD)" >> "$GITHUB_OUTPUT"
   ```
4. **Compute the build date** in ISO 8601 UTC into a step output:
   ```bash
   echo "date=$(date -u +%Y-%m-%dT%H:%M:%SZ)" >> "$GITHUB_OUTPUT"
   ```
5. `docker/setup-buildx-action@v3` — required for the cache backend below.
6. Log into your registry (Docker Hub or GHCR — see "Registry options" below).
7. `docker/build-push-action@v6` with:
   - `context: .`
   - `push: true`
   - `build-args:` populated with `VERSION`, `COMMIT_SHA`, `BUILD_DATE` from the outputs above.
   - `tags:` — **both** of these, comma-separated or one per line:
     - `<your-image-name>:<version>`
     - `<your-image-name>:<version>-<short-sha>`
   - `cache-from: type=gha`
   - `cache-to: type=gha,mode=max`
8. Expose the version, SHA, date, and the `digest` output from `build-push-action` as **job outputs** so the next job can use them.

**Tag policy:**

- **Both tags are required.** `<version>` is the human-readable release identifier. `<version>-<short-sha>` is the **immutable identifier** — if you ever rebuild `1.0.0` for any reason, the SHA-suffixed tag still uniquely identifies which build is which. That is the core of immutable artifact thinking.
- **Do NOT push `latest`.** `latest` is a mutable, ambiguous identifier — it contradicts everything this lab teaches.

**Why the Buildx GHA cache:** Teaches that Docker layer reuse in CI depends on the Dockerfile structure you wrote in Part 2. The `deps` / `builder` split is what makes the cache effective. Connect the file structure to the CI performance.

### Job 4: `release-artifact`

**Depends on:** `docker-release`.

**Goal:** Generate a `release.json` manifest and upload it as a workflow artifact.

**Required steps:**

1. Consume the outputs from `docker-release` (version, sha, date, digest).
2. Construct `release.json` matching the **exact schema** below — same keys, same casing, same order.
3. Upload via `actions/upload-artifact@v4` with the name `release-manifest`.

#### `release.json` — exact schema

```json
{
  "version": "1.0.0",
  "commitSha": "abc1234",
  "buildDate": "2026-05-27T10:00:00Z",
  "imageName": "lironefitoussi/company-api",
  "imageTags": [
    "lironefitoussi/company-api:1.0.0",
    "lironefitoussi/company-api:1.0.0-abc1234"
  ],
  "imageDigest": "sha256:...",
  "runNumber": "42"
}
```

- Keys are **camelCase**, in the order shown.
- `runNumber` comes from `${{ github.run_number }}`.
- `imageDigest` is the **registry digest** returned by the push step (`steps.<id>.outputs.digest`), not a local image ID.

This file is the **single source of truth for "what shipped."** Grading validates it parses, contains every required key, and that no value is empty.

## Registry options

Pick one. Document your choice in your submission.

### Option A — Docker Hub (primary)

1. Create a Docker Hub account (free).
2. Create a public repo named `company-api` under your username.
3. Create an access token (Account Settings → Security → New Access Token, **read-write**).
4. In your **GitHub** repo settings → Secrets and variables → Actions, add:
   - `DOCKERHUB_USERNAME` — your Docker Hub username
   - `DOCKERHUB_TOKEN` — the access token from step 3
5. Image name in your workflow: `<your-username>/company-api`.

### Option B — GHCR (lower friction, recommended if you're new)

1. No account setup — GitHub gives you `ghcr.io/<your-username>` for free.
2. The default `GITHUB_TOKEN` can push to GHCR — no separate secret needed.
3. Add this to your `docker-release` job: `permissions: { packages: write, contents: read }`.
4. Log in with `docker/login-action@v3` using `registry: ghcr.io`, `username: ${{ github.actor }}`, `password: ${{ secrets.GITHUB_TOKEN }}`.
5. Image name in your workflow: `ghcr.io/<your-username>/company-api`.
6. **OCI image names must be lowercase.** If your GitHub username has any uppercase letters (e.g. `LironeFitoussi`), `${{ github.repository_owner }}` will preserve the case and the push will fail with `repository name must be lowercase`. Lowercase it explicitly inside a step before using it in tags:

   ```bash
   echo "image=ghcr.io/$(echo '${{ github.repository_owner }}' | tr '[:upper:]' '[:lower:]')/company-api" >> "$GITHUB_OUTPUT"
   ```

   Then reference `${{ steps.<id>.outputs.image }}` in your `tags:` block. (Docker Hub usernames are already lowercase, so this only bites GHCR users.)

### Secrets vs. metadata — a real lesson

`DOCKERHUB_TOKEN` is a **secret** — it goes in repo secrets, never in code, never echoed in logs.

`VERSION`, `COMMIT_SHA`, `BUILD_DATE` are **not secret** — they are public release metadata. They go in `build-args`, not in secrets. Putting non-secrets in secrets is a common mistake that hides debugging information for no security gain.
