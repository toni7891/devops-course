01
Object Management

Three Ways to Manage Objects

01 / IMPERATIVE CLI
⌨️

Imperative Commands

Type commands directly in the terminal. Fast, but nothing is saved.

kubectl run nginx --image=nginx kubectl delete pod nginx
✓ Fast & simple
✓ Great for learning
✗ Hard to reproduce
✗ No history / version control
02 / IMPERATIVE FILES
📄

Imperative with Config Files

Use files, but tell K8s the action explicitly (create / replace).

kubectl create -f pod.yaml kubectl replace -f pod.yaml
✓ Files are reusable
✓ Stored in version control
✗ You manage the state
✗ Easy to make mistakes
03 / DECLARATIVE ★
✨

Declarative with Apply

Tell K8s what you want. It figures out what to create/update/delete.

kubectl apply -f pod.yaml kubectl apply -f ./configs/
✓ Kubernetes manages state
✓ Safe to run repeatedly
✓ Recommended for production
💡 Key insight: With declarative, you just say "I want 3 replicas of nginx". Kubernetes compares that to the current state and does whatever is needed — create, update, or nothing.
YAML Manifest

Anatomy of a Manifest

# Every K8s YAML has 4 required fields

①  apiVersion: v1

②  kind: Pod

③  metadata:
     name: my-nginx
     labels:
       app: nginx
       env: production

④  spec:
     containers:
     - name: nginx
       image: nginx:1.25
       ports:
       - containerPort: 80
①
apiVersion

Which API group and version to use. v1, apps/v1, batch/v1…

②
kind

The type of object. Pod, Service, Deployment, ConfigMap, etc.

③
metadata

Name, namespace, labels, annotations. How Kubernetes identifies and finds this object.

④
spec

The desired state. What containers to run, what volumes to mount, what ports to expose, etc.

Section 02

Services
Deep Dive

Pods are temporary. Services are stable. Here's why that matters and how services work.

02
The Problem

Why Do We Need Services?

Pods are ephemeral. When a pod dies and restarts, it gets a new IP address. If your frontend is connecting directly to a pod IP — that connection breaks. 💥

WITHOUT A SERVICE — BROKEN

Frontend
→
pod-abc · 10.0.0.5 ☠️
pod-xyz · 10.0.0.9 ✓ NEW
Frontend still points to 10.0.0.5 → Connection refused!

WITH A SERVICE — STABLE ✓

Frontend
→
Service
10.0.0.100 (stable)
→
pod-abc · 10.0.0.5 ☠️
pod-xyz · 10.0.0.9 ✓
Service always has the same IP & DNS name. It routes to whatever pods match its selector.
How It Works

Services Find Pods via Selectors

The Service

apiVersion: v1
kind: Service
metadata:
  name: nginx-svc
spec:
  selector:
    app: nginx   # ← Match pods with this label
  ports:
  - port: 80        # Service port
    targetPort: 80  # Pod port

Matched Pods

pod-abc
appnginx envprod
✓ Matched
pod-xyz
appnginx
✓ Matched
pod-def
appredis
✗ Not matched
🔑 The Service gets a stable ClusterIP and a DNS name (e.g. nginx-svc.default.svc.cluster.local). It load-balances across all matched pods automatically.
Service Types

4 Types of Services

🔒

ClusterIP Default

Accessible only inside the cluster. Perfect for internal communication between microservices. Gets a virtual IP within the cluster network.

type: ClusterIP
Port range: cluster internal only
🚪

NodePort

Opens a port on every node in the cluster (30000–32767). Traffic hits any node on that port and gets routed to the service.

type: NodePort
External: NodeIP:30080 → Pod:80
☁️

LoadBalancer

Provisions a cloud load balancer (AWS ELB, GCP LB…). Gets a real external IP. The recommended way to expose services to the internet.

type: LoadBalancer
Cloud provider creates the LB for you
🔗

ExternalName

Maps the service name to an external DNS name. No proxy — just a CNAME record. Useful to access external services from inside the cluster.

type: ExternalName
externalName: api.example.com
ACCESS SCOPE ————————————————————————————————————
ClusterIP → NodePort → LoadBalancer → ExternalName
Internal only Internet / External

03
Labels & Selectors

Labels — Tags for Your Objects

Labels are key=value pairs attached to any Kubernetes object. They're how you group, find, and connect objects.

frontend-pod
appfrontend envprod versionv2
backend-pod
appbackend envprod tierapi
staging-pod
appfrontend envstaging

Equality-Based Selectors

# kubectl filter
kubectl get pods -l env=prod
kubectl get pods -l env!=staging

# In YAML selector:
selector:
  matchLabels:
    env: prod

Set-Based Selectors

# More powerful filtering
kubectl get pods -l 'env in (prod,staging)'
kubectl get pods -l 'env notin (dev)'
kubectl get pods -l 'tier' # key exists

matchExpressions:
- key: env
  operator: In
  values: [prod, staging]
Annotations

Annotations — Metadata Without Filtering

Annotations are also key-value pairs, but they're meant for tools and config, not for selecting/filtering objects. They can hold larger, more complex values.

Labels
  • Short key=value
  • Used for filtering
  • Used by selectors
  • Organizing objects
Annotations
  • Any size value
  • NOT used for filtering
  • For tools / config
  • Ingress, CI/CD info…

Real example — Ingress Nginx config

metadata:
  name: my-ingress
  annotations:
    # Config for the Ingress Controller
    nginx.ingress.kubernetes.io/rewrite-target: /
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
    nginx.ingress.kubernetes.io/proxy-body-size: 10m
    kubernetes.io/ingress.class: nginx
💡 The Ingress controller reads these annotations to configure itself — Kubernetes itself doesn't understand them.
Namespaces

Namespaces — Virtual Clusters 🏢

Think of a cluster as an apartment building. Namespaces are the individual apartments — isolated spaces that share the same infrastructure.

🏢 Cluster
namespace: production
frontend-pod · backend-pod · db-pod
namespace: staging
frontend-pod · backend-pod
namespace: monitoring
prometheus · grafana
namespace: kube-system
coredns · kube-proxy

Benefits

  • Isolate teams / environments
  • Apply RBAC per namespace
  • Set resource quotas per namespace
  • Same name, different namespaces = no conflict

Cross-Namespace DNS

# Inside same namespace:
nginx-svc

# From another namespace:
nginx-svc.production.svc.cluster.local

# Format:
{service}.{namespace}.svc.cluster.local
Resource Management

Requests, Limits & Quotas

Container Level

Per-container resource guarantee & cap

resources:
  requests:       # Minimum guaranteed
    memory: "64Mi"
    cpu: "250m"
  limits:         # Maximum allowed
    memory: "128Mi"
    cpu: "500m"
CPU250m request / 500m limit
Memory64Mi request / 128Mi limit

Namespace Level (ResourceQuota)

Total cap for an entire namespace

kind: ResourceQuota
spec:
  hard:
    pods: "10"           # Max 10 pods
    requests.cpu: "2"    # 2 CPU total
    requests.memory: 4Gi
    limits.cpu: "4"
    limits.memory: 8Gi
Request = "I need at least this much" — used by scheduler to place the pod
Limit = "I must never use more than this" — CPU is throttled; exceed memory = OOMKill
Health Probes

Health Probes — Automatic Health Checks

Kubernetes runs these checks automatically and takes action when they fail.

🚀

Startup Probe

Runs first. Gives slow-starting apps time to boot. Liveness & readiness wait until this passes.

fails → kill & restart
→
💓

Liveness Probe

Runs continuously. Is the container still alive? If it fails, the container is restarted.

🔄 repeats forever
fails → restart pod
→
✅

Readiness Probe

Runs continuously. Is the container ready to serve traffic? If it fails, removed from Service endpoints.

🔄 repeats forever
fails → remove from LB

Probe Types

livenessProbe:
  httpGet:            # HTTP 200 = healthy
    path: /healthz
    port: 8080
  initialDelaySeconds: 10   # Wait before first check
  periodSeconds: 5          # Check every 5s
  failureThreshold: 3       # 3 fails = restart
# Other types: exec (run command), tcpSocket (check TCP port)

Containers Lose Data When They Die 💀

WITHOUT VOLUMES

Container
+ data: /var/data
💥
Container
data: GONE
→
New Container

WITH A VOLUME ✓

Container
mounts /data
↕
📦 Volume
data lives here
💥
↕
New Container
mounts same /data
Volume outlives the container — data is safe ✓
Volume Types

Volume Scope — Where Does Data Live?

🏗️ CLUSTER SCOPE
PersistentVolume (PV) — exists independently of pods & nodes
🖥️ NODE SCOPE
Local Volume — tied to a specific node's disk
📦 POD SCOPE
emptyDir — shared between containers, deleted with pod

📦 emptyDir

  • Created when pod starts
  • Shared between containers in same pod
  • Deleted when pod is removed
volumes:
- name: cache
  emptyDir: {}

🖥️ Local Volume

  • Uses a directory on a specific node
  • Survives pod restarts
  • Requires nodeAffinity
volumes:
- name: local-data
  local:
    path: /mnt/data

☁️ PersistentVolume

  • Cluster-level storage resource
  • Survives pod AND node
  • Claimed via PVC (see next slide)
# Claimed via PVC ↓
volumes:
- name: data
  persistentVolumeClaim:
    claimName: my-pvc

Access Modes

PV Access Modes & Reclaim Policies

Access Modes

ModeFull NameMeaningExample Use
RWO ReadWriteOnce 1 node can read & write Database (MySQL)
RWOP ReadWriteOncePod 1 pod can read & write Strict single-writer
RWX ReadWriteMany Many nodes read & write Shared file storage (NFS)
ROX ReadOnlyMany Many nodes read only Static assets, configs

Reclaim Policies

Retain
PV is kept after PVC is deleted. Admin must manually reclaim. Safe for data
Delete
PV and underlying storage are deleted automatically. Data deleted!
Recycle ⚠️
Wipes data (rm -rf) and makes PV available again. Deprecated
StatefulSets

StatefulSets vs Deployments

Use StatefulSets when each pod needs a stable identity and its own persistent storage — like databases.

🚀 Deployment

Pods are interchangeable. Random names. Shared or no storage.

pod-7d9f8b-xqrzt
pod-7d9f8b-plmkj
pod-7d9f8b-bnvca
  • Pods created in any order
  • Deleted all at once (scale down)
  • Random generated names
  • Usually one shared PVC or none

🗄️ StatefulSet

Pods have stable identity, ordered creation, own PVC per pod.

mysql-0 · PVC: data-mysql-0
mysql-1 · PVC: data-mysql-1
mysql-2 · PVC: data-mysql-2
  • Created in order: 0, 1, 2…
  • Deleted in reverse: 2, 1, 0
  • Stable hostname: {name}-{index}
  • Each pod gets its own PVC
🔗 Headless Service pairs with StatefulSets — set clusterIP: None. Gives each pod stable DNS: mysql-0.mysql-svc.default.svc.cluster.local
